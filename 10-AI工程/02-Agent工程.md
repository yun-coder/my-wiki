# Agent 工程

> 这页解决一个问题：**什么时候该做 Agent、怎么搭不失控、失败长什么样。**

## 一、先判断该不该做 Agent

Agent = 模型 + 状态 + 工具 + 目标 + 执行循环 + 结果验证。少任何一项，它就是个带循环的聊天框。

| 任务特征 | 适合 | 不适合 |
|---|---|---|
| 步骤数 | 3 步以上、路径不完全固定 | 一步能做完（直接用提示词或脚本） |
| 中间结果 | 需要根据上一步结果决定下一步 | 流程完全确定（用工作流引擎） |
| 工具 | 需要读文件、查库、调 API、操作浏览器 | 只需生成文本 |
| 验证 | 有可判定的成功标准 | 无法判断对错 |
| 出错代价 | 可回滚、可人工接管 | 涉及资金、合同、不可逆删除 |

**判断**：流程固定的用工作流，步骤开放的用 Agent，两者混着用最常见——工作流负责边界，Agent 负责边界内的判断。

## 二、最小可用 Agent 的六个部件

1. **系统提示**：角色、边界、工具使用规则、输出格式、什么时候停下来问人。
2. **状态**：任务目标、已完成步骤、中间产物、剩余预算。状态要能落盘，不能只在上下文里。
3. **工具**：每个工具一个明确契约（输入 schema、返回结构、失败语义）。
4. **循环**：计划 → 执行 → 观察 → 修正，设最大步数与超时。
5. **验证**：每步或最终结果的可判定检查（测试、schema 校验、规则、第二模型审查）。
6. **出口**：成功返回、失败报告、需要人工介入三种结局都要显式设计。

## 三、架构选择

| 架构 | 适用 | 代价 |
|---|---|---|
| 单 Agent + 工具集 | 大多数业务任务 | 上下文会变长，需要压缩 |
| 图 / 状态机编排（LangGraph 类） | 步骤长、需要断点恢复、有分支 | 设计成本高，图会变复杂 |
| 多 Agent 角色分工 | 需要并行探索、独立审查、不同专长 | 上下文传递损耗、协调成本、结果不可复现 |
| 子代理树（主 Agent 派生子任务） | 大量独立同构任务、需要隔离上下文 | 汇总质量取决于主 Agent，子任务失败要能局部重试 |

**经验法则**：先单 Agent，出现"上下文爆炸"或"需要独立审查"时再拆。拆的时候按**产物边界**拆（一个子任务交付一个文件/一份结论），不按"人格"拆。

## 四、上下文工程

Agent 失败十次有七次是上下文问题，不是模型问题。

- **先检索再塞**：不要把整个知识库放进系统提示，按任务检索相关片段。
- **外置状态**：中间产物写文件，上下文只留路径与摘要；需要时再读回。
- **压缩策略**：会话超过阈值就摘要成"已确认事实 + 待办 + 约束"，丢掉过程噪声。
- **子任务隔离**：一个子代理只带它需要的信息，避免主上下文被污染。
- **约束重复**：关键限制（预算、禁止操作、输出格式）在开头和结尾各出现一次。

## 五、工具设计

工具是 Agent 的手，手不稳，脑子再强也没用。

- **契约清晰**：参数名、类型、必填、枚举值、返回结构写死；错误返回可读的原因，不要只返回 `error`。
- **最小权限**：只读工具与写入工具分开；删除、支付、发信这类操作单独授权。
- **幂等**：重试不应该产生重复订单、重复邮件。
- **可审计**：每次调用记录参数、结果、耗时、调用者。
- **粒度**：工具太少 Agent 只能瞎猜，太多会选错；按"一个业务动作一个工具"设计。
- **防注入**：工具返回的外部内容（网页、邮件、文档）标记为数据，不得当作指令执行。

## 六、技能（Skill）作为能力封装

把一类任务的做法写成结构化技能，比写一个巨型提示词可靠得多。一个合格技能至少包含：

```text
触发条件   什么任务该用它（关键词、场景、前置条件）
输入输出   需要什么、产出什么格式
步骤       可复现的执行顺序，含分支与停止条件
权限边界   能改什么、不能改什么、哪些操作要人确认
失败处理   常见错误与对应动作
验证方式   怎么判断做完了、做对了
```

为什么有效：技能把"隐性经验"变成"可加载的显式流程"，模型不必每次重新推理；人也容易审查和迭代。

本机 DSH 已装 19 个技能，覆盖图表、PPT、视频、文档、检索、浏览器等，见 [DSH技能手册](../30-DSH能力/DSH技能手册.md)。自建技能的写法可以参考 `skills原文/shot-contract`（含 13 道确定性质量门）。

## 七、MCP 与外部系统

MCP 解决"统一接入外部工具与数据"的问题，但接入不等于安全：

- 一个 MCP 服务器暴露的每个工具都要单独评估权限。
- 优先选择支持只读、可限流、可审计的实现。
- 跨系统写操作先做影子模式（只生成计划不执行），确认后再放开。
- 服务器挂了要有超时与降级，不能让 Agent 卡死。

## 八、长任务

长任务（>10 分钟、跨会话）必须解决四件事：

1. **持久状态**：目标、进度、产物落盘；进程重启能续跑。
2. **断点与幂等**：同一步重复执行不产生副作用。
3. **预算硬停止**：token、时间、工具调用次数都有上限。
4. **进度可见与人工接管**：能看"现在到哪一步"，能暂停、改方向、接管。

## 九、记忆

分三层，别混用：

| 层 | 存什么 | 生命周期 | 风险 |
|---|---|---|---|
| 会话记忆 | 当前任务的上下文 | 一次会话 | 上下文超长后退化 |
| 项目记忆 | 项目状态、决策、约定 | 项目周期 | 过期不清理会误导 |
| 长期记忆 | 偏好、事实、关系、承诺 | 长期 | 冲突、隐私、删除困难 |

长期记忆的关键不是"存得多"，而是**冲突消解与可撤回**：新事实覆盖旧事实、过期自动降权、用户可删除。没有这三条的记忆系统，用三个月就会变成噪声源。

## 十、反模式清单

- 用 Agent 做确定性流程（本来 50 行脚本能搞定）。
- 没有退出条件，循环到 token 烧完。
- 工具返回什么就往上下文里塞什么，几轮之后全是噪声。
- 多 Agent 互相"讨论"，没有裁决者，结论取决于谁最后说话。
- 把审批做成形式：人永远点"同意"，等于没有审批。
- 用自然语言描述验收标准，却从不写断言。

## 十一、落地顺序

1. 用人工流程跑通一遍，记录每一步的输入输出与判断点。
2. 找出可判定的步骤，先自动化它们（通常占 70% 工作量但风险最低）。
3. 把剩余判断点做成 Agent 的一次决策，保留人工确认。
4. 统计人工修改率，逐步扩大自动化比例。
5. 有了稳定失败模式后，再考虑多 Agent 或自建工具。
