# 模型与推理部署

> 这页解决一个问题：**给定一个任务，选哪个模型、走哪种部署、怎么保证不贵也不断。**

## 一、选型方法：先任务集，后模型

公开榜单衡量的是平均能力，你的业务只关心特定任务上的失败率、成本、延迟。所以顺序固定：

1. 把真实任务切成 20–50 条样本，写清输入与"什么算对"。
2. 用 2–3 个候选模型跑同一套样本，记录四列：正确率、单次成本、P95 延迟、失败类型。
3. 选"失败类型可接受"的那个，而不是分数最高的那个。
4. 模型换代后重跑同一套样本，再改结论。

失败类型比正确率更重要：翻译任务错一个术语和错一个数字，代价完全不同。

**判断**：生产系统至少保留两条路径——主用直连（稳定、可计价），备用聚合（切换快、可应急）。只接一家聚合平台，等于把可用性外包给别人的路由。

## 三、部署形态怎么选

| 形态 | 什么时候选 | 代价 |
|---|---|---|
| 云 API | 绝大多数场景；流量波动大、不想运维 | 数据出域、长期成本随量线性增长 |
| 本地小模型（Ollama / llama.cpp） | 数据不能出门、任务简单（分类、抽取、改写）、离线环境 | 能力上限低，复杂推理会明显掉 |
| 自建推理服务（vLLM / SGLang） | 有稳定高并发、要控单位成本、有 GPU 运维能力 | 显存规划、批处理调参、故障自愈都要自己做 |
| 边缘 / 端侧 | 实时性要求高、无网、隐私极敏感 | 模型尺寸受限，效果需重新评测 |

一个实用组合：**云端强模型做规划与难例，本地小模型做批量预处理与初筛**。成本能降一个数量级，且失败可回退。

## 四、成本模型

成本 ≈（输入 token × 单价）+（输出 token × 单价）+ 重试与失败浪费。可设计的杠杆：

- **分层**：分类、抽取、改写用便宜模型；规划、多步推理、代码用强模型。
- **缓存**：系统提示、知识库文档、few-shot 示例加前缀缓存，重复部分按缓存价计。
- **批处理**：离线任务走批处理接口，通常有折扣，代价是延迟。
- **压缩上下文**：先检索再塞，不要整篇文档进 prompt；长会话定期摘要。
- **硬预算**：每个任务设 token 上限与重试上限，超限直接失败并告警，避免死循环烧钱。

粗略心算：一次"读 5 页文档 + 写 800 字"的任务，输入约 6k–10k token、输出约 1.5k token。用便宜模型是分级钱，用旗舰模型是几毛到一块。批量做 1000 条之前，先算清楚。

## 五、稳定性

- **超时与重试**：区分"可重试"（限流、5xx）与"不该重试"（内容违规、参数错），重试要退避。
- **限流**：按供应商配额做令牌桶，别等 429 才降速。
- **结构化输出**：优先用 JSON Schema / 工具调用约束；拿不到就做一次校验 + 修复，不要让脏 JSON 流进下游。
- **版本漂移**：把模型 id 固定到具体版本，不要用 `latest`；升级当变更管理走。
- **降级链**：主模型 → 备用模型 → 规则兜底；每一级都要能输出可用结果，而不是报错。

## 六、常见坑

| 坑 | 表现 | 处理 |
|---|---|---|
| 长上下文退化 | 文档很长时忽略中段、漏掉约束 | 关键约束前置与后置各说一次；分段处理再汇总 |
| 结构化输出不稳定 | 偶发多余文字、字段缺失 | Schema 约束 + 解析失败重试（最多 2 次） |
| 中文标点与数字 | 全角/半角混用、数字被改写 | 后处理规范化；金额、单号走规则校验 |
| 流式中断 | 前端已显示一半，后端超时 | 服务端保存完整结果，前端可重连取全文 |
| 计价口径误判 | 以为按次，实际按 token 且含缓存读写 | 上线前用真实调用对账一次 |

## 七、本机现状（2026-11）

- 日常推理走 DeepSeek 系列（含快速档），长文档与代码任务用强档；Agnes 平台作为个人实验通道。
- 视频/图像生成不走文本模型，走 EasyFrame（MiniMax-H3）与本机号池，链路见 [DSH实战要点](../30-DSH能力/DSH实战要点.md)。
- 聚合平台只在需要横向比价或切换模型时临时接。
